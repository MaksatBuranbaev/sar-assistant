# Аналитический ассистент ПСС МЧС 🚒

Text-to-SQL ассистент над журналами выездов и занятий поисково-спасательной службы.
Пользователь задаёт вопрос на русском языке — GigaChat строит SQL-запрос,
запрос проверяется и выполняется в PostgreSQL, результат возвращается текстом и таблицей.

Задача, которую он решает: чтобы получить цифру из журналов, аналитику нужно было
писать SQL вручную, а диспетчеру — ждать аналитика.

---

## Как это работает

```
Вопрос пользователя
        │
        ├─► retriever.py       поиск k похожих примеров «вопрос → SQL» (TF-IDF)
        ├─► db.get_schema()    схема из information_schema + частые значения колонок
        │
        ├─► GigaChat #1        генерация SQL по схеме, примерам и истории диалога
        │
        ├─► sql_guard.py       разбор в AST: один SELECT, только свои таблицы,
        │                      без опасных функций, принудительный LIMIT
        │
        ├─► db.py              выполнение под read-only ролью с таймаутом
        │        │
        │        └── ошибка ──► текст ошибки возвращается модели вместе с её же
        │                       запросом, генерация повторяется (self-correction)
        │
        └─► GigaChat #2        пересказ результата на русском языке
```

| Файл | Назначение |
|---|---|
| `app.py` | Streamlit-интерфейс, история диалога |
| `assistant.py` | пайплайн: промпты, вызовы модели, self-correction |
| `sql_guard.py` | валидация сгенерированного SQL по AST |
| `db.py` | пул соединений, интроспекция схемы, выполнение запросов |
| `retriever.py` | поиск похожих примеров для few-shot промпта |
| `config.py` | настройки из окружения |
| `sql/` | схема, роль только на чтение, демо-данные |
| `eval/` | размеченный набор и замер execution accuracy |
| `tests/` | тесты валидатора, ретривера и разбора ответа модели |

## Безопасность

Ассистент выполняет в боевой базе SQL, сгенерированный языковой моделью.
Модель можно склонить к чему угодно текстом запроса, поэтому защита не может
опираться на промпт — она сделана слоями, и каждый работает без остальных.

**Слой 1. Права в СУБД** (`sql/readonly_role.sql`) — основной.
Роль `pss_readonly` имеет `GRANT SELECT` ровно на две таблицы и не имеет права
создавать объекты. `DELETE` не выполнится, даже если пройдёт все проверки выше.
Здесь же `default_transaction_read_only`, `statement_timeout`, `lock_timeout`.

**Слой 2. Параметры соединения** (`db.py`) — те же ограничения задаются через
libpq `options`, поэтому действуют даже если БД развернул кто-то другой и роль
настроить забыли.

**Слой 3. Разбор запроса** (`sql_guard.py`) — то, что правами не закрывается:

| Что блокируется | Почему прав недостаточно |
|---|---|
| `SELECT 1; DELETE FROM ...` | формально начинается с SELECT |
| `SELECT * FROM pg_user` | системные каталоги читаемы роли PUBLIC, и отобрать это, не сломав драйвер, нельзя |
| `SELECT pg_sleep(600)` | это корректный SELECT, права его не остановят |
| обращение к таблице вне allowlist | новая таблица с персональными данными не должна стать видимой сама собой |
| отсутствие `LIMIT` | защита от выгрузки всей таблицы в интерфейс |

Проверка идёт по AST, а не регулярками: текстовая проверка вида
`sql.upper().startswith("SELECT")` даёт одновременно ложные срабатывания
(легальный `WITH ... SELECT` отвергается) и пропуски (`SELECT 1; DROP ...`).

Каждый пункт таблицы закрыт тестом в `tests/test_sql_guard.py`.

**Что осознанно НЕ сделано:** маскирование персональных данных. В `description_raw`
и `address` попадают адреса и обстоятельства происшествий, и при пересказе
результата они уходят в модель. Для боевой эксплуатации эти колонки нужно либо
исключить из выдачи, либо маскировать до отправки в LLM.

## Качество генерации

Промпт — изменяемый артефакт, как и код: правка, которая чинит один вопрос,
молча ломает три других. Поэтому качество измеряется, а не оценивается на глаз.

```bash
python -m eval.run_eval
```

Скрипт прогоняет размеченный набор `eval/dataset.yaml` (30 вопросов, разбитых на
easy / medium / hard) и считает **execution accuracy** — долю вопросов, где
результат сгенерированного запроса совпал с результатом эталонного.
Сравниваются именно результаты, а не тексты запросов: один и тот же ответ даёт
множество разных корректных SQL, и сравнение текстов мерило бы совпадение стиля.

Дополнительно считаются доля невалидного SQL, доля ошибок БД, доля неверных
результатов и latency p50/p95. Отчёт сохраняется в `eval/report.json`.

Тестовый набор не пересекается с банком few-shot примеров — это проверяется
отдельным тестом. Иначе модель получала бы эталонный ответ прямо в промпте, и
метрика показывала бы утечку, а не качество.

## Запуск

### Через Docker (поднимает и БД, и приложение)

```bash
cp .env.example .env        # заполните GIGACHAT_CREDENTIALS
docker compose up --build
```

Открыть http://localhost:8501. PostgreSQL при первом запуске сам применит схему,
создаст read-only роль, выставит ей пароль из `PSS_READONLY_PASSWORD` и загрузит
синтетические демо-данные (600 выездов, 300 занятий) — приложение работает сразу,
без доступа к реальным журналам.

Порт приложения публикуется только на `127.0.0.1`, порт PostgreSQL наружу не
публикуется вовсе: у ассистента нет аутентификации, а за ним стоит база.
Для реального развёртывания впереди нужен обратный прокси с авторизацией.

Пересоздать стенд с нуля (init-скрипты выполняются только при пустом томе):

```bash
docker compose down -v && docker compose up --build
```

### Локально

```bash
python -m venv env
source env/Scripts/activate          # Windows: env\Scripts\activate
pip install -r requirements.txt

psql -U postgres -d pss_db -f sql/schema.sql
psql -U postgres -d pss_db -f sql/readonly_role.sql
psql -U postgres -d pss_db -f sql/seed_demo.sql    # опционально, демо-данные

cp .env.example .env
streamlit run app.py
```

### Тесты

```bash
pip install -r requirements-dev.txt
pytest        # не требуют ни PostgreSQL, ни ключей GigaChat
ruff check .
```

## Ограничения и что дальше

Честный список того, чего в проекте нет:

- **Плотные эмбеддинги.** Поиск примеров лексический (TF-IDF на символьных
  n-граммах). На корпусе в несколько десятков однотипных вопросов этого хватает,
  но перефразировки без общих слов он не найдёт. Следующий шаг — эмбеддинги и
  `pgvector`, благо PostgreSQL уже в стеке.
- **Схема из двух таблиц целиком влезает в промпт.** Когда таблиц станут десятки,
  понадобится retrieval и по самой схеме, а не только по примерам.
- **Нет трассировки запросов.** Для эксплуатации нужен полный след
  «вопрос → промпт → SQL → результат → ответ» с сохранением, иначе разбирать
  жалобы пользователей не на чем.
- **Нет кэша.** Аналитики задают одни и те же вопросы; кэш пары
  «нормализованный вопрос → SQL» убрал бы половину вызовов модели.
- **Streamlit блокирует.** Для нескольких одновременных пользователей нужен
  вынос пайплайна в асинхронный API, а интерфейс — отдельно.
